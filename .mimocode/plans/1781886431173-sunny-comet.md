# Fix Session Expired (419) on Login/Logout

## Root Cause

The app is a React SPA served by Laravel. CSRF tokens are embedded in `<meta name="csrf-token">` at initial page load and never refreshed client-side. Two problems:

1. **After logout**: `logout()` destroys the server session, but the SPA navigates to `/login` via React Router (client-side, no page reload). The CSRF token in the meta tag is **stale** (belongs to the destroyed session). When the user submits the login form → 419 CSRF mismatch.

2. **After session expires**: Same issue — the SPA holds a stale CSRF token. On the next POST (login, etc.) → 419.

3. **After login succeeds**: Laravel regenerates the session ID (security best practice), which invalidates the old CSRF token. Subsequent SPA navigation uses client-side routing with the stale meta CSRF token. If any Fortify form (e.g., logout) is triggered, it may fail.

## Plan

### 1. Force full page reload after logout (most critical fix)

**Files to change:**
- `resources/js/auth.ts` — `logout()` function
- `resources/js/components/layout/AdminLayout.tsx` — `handleLogout`
- `resources/js/pages/dashboards/Client.tsx` — `handleLogout`
- `resources/js/components/nav/NavUser.tsx` — already correct (uses `window.location.href`)

**What to do:**
- In `resources/js/auth.ts`, after the `fetch('/logout')` call and `clearAuthUser()`, force a full page reload to `/login` via `window.location.href = '/login'`. This ensures a fresh session and fresh CSRF token.
- Remove the `navigate('/login', { replace: true })` calls in `AdminLayout.tsx` and `Client.tsx` after `logout()` since `logout()` itself will handle the redirect. Or make `logout()` accept an optional redirect URL.

### 2. Fix login to reload page instead of SPA navigation after success

**File to change:**
- `resources/js/pages/general/Login.tsx`

**What to do:**
- After a successful login, the server regenerates the session ID. The meta CSRF token is now stale. Instead of `navigate(redirectAfterLogin(user.role), { replace: true })`, use `window.location.href = redirectAfterLogin(user.role)` to force a full page reload. This ensures:
  - A fresh CSRF token is available for the new session
  - All stale state is cleared

### 3. Fix register to reload page after success

**File to change:**
- `resources/js/pages/general/Register.tsx`

**What to do:**
- After successful registration (Fortify auto-logs the user in and regenerates the session), use `window.location.href = '/dashboard'` instead of `navigate('/dashboard')`.

### 4. Improve 419 error handling to auto-recover

**File to change:**
- `resources/js/api/http.ts`

**What to do:**
- On 419 response, instead of navigating to `/session-expired` (a static error page requiring manual refresh), automatically reload the current page: `window.location.reload()`. The fresh page load will create a new session with a valid CSRF token, and the user can retry their action.

### 5. Ensure session is created on initial visit

**Already working** — Laravel's `StartSession` middleware (in the `web` group) automatically creates a session on the first request. The CSRF token in the Blade template is generated from this session. No changes needed.

## Verification

2. After login → navigate to admin/client dashboard → logout → redirected to `/login` → login again → should work
3. Wait for session to expire (or manually delete session from DB) → try any action → should auto-reload and recover
4. Register a new user → should redirect to dashboard without 419
5. Open multiple tabs → login in one tab → other tab should still work (session cookie is shared)
