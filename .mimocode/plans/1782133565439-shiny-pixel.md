# E2E Flow Audit & Professional Improvements

## Audit Summary

Traced the entire flow: **Booking → Payment → Confirmation → Complaint → Refund → Admin Actions → Notifications**

Found **6 critical gaps**, **8 medium issues**, and **4 improvements** needed.

---

## CRITICAL GAPS (Must Fix)

### C1: No Emails Sent Anywhere
**All 7 notification classes use `['database']` only.** No `toMail()` method, no Mailable classes, no Blade email templates. Customers never receive:
- Booking confirmation email
- Payment receipt email
- Payment failure email
- Complaint acknowledgment email
- Admin reply email
- Refund approval/rejection email

**Fix:** Add `toMail()` to all notification classes + create email Blade templates.

### C2: Payment Callback is Unauthenticated GET
`GET /api/payment/callback` can be called by anyone who knows the `orderId` and `booking_id`. An attacker could craft a URL to mark any booking as paid without paying.

**Fix:** Add HMAC signature verification to the callback. ClictoPay should send a signature; we verify it before processing.

### C3: No Amount Verification in Callback
The callback doesn't verify that the amount paid matches `booking.total_amount`. A tampered response could confirm a different amount.

**Fix:** Compare `verification['amount']` against `booking->total_amount` in the callback.

### C4: No Actual Refund Processing
When admin marks a complaint as "refunded", no money is returned through ClictoPay. The booking status isn't updated either.

**Fix:** Add `refundPayment()` to ClictoPayService + update booking status to "Cancelled" on refund.

### C5: Complaint Reply Overwrites Previous Replies
`admin_reply` is a single JSON field. Each admin reply replaces the previous one. No conversation thread.

**Fix:** Add a `complaint_replies` table or convert `admin_reply` to a JSON array of replies with timestamps.

### C6: No Client Notification on Complaint Resolution
Client gets notified when admin replies, but NOT when the complaint is resolved or rejected.

**Fix:** Add notification in `AdminComplaintController::resolve()` and when status changes to "rejected".

## MEDIUM ISSUES (Should Fix)

### M1: No Idempotency on Payment Callback
If user refreshes the callback page, notifications fire multiple times.

**Fix:** Check if payment is already `paid` before processing.

### M2: No Admin Notification on New Booking (from payment)
`BookingController::store()` notifies admin of "booking.created", but when payment completes via callback, admin gets "booking.paid" which maps to the default case in `BookingActivityNotification::message()`. The message template doesn't have a "paid" case.

**Fix:** Add `'booking.paid'` case to `BookingActivityNotification::message()`.

### M3: No Payment Retry Button
If payment fails, client sees a result page with no way to retry. They must go back to dashboard and find the booking.

**Fix:** Add "Retry Payment" button on PaymentResult failure page + "Pay Now" button on pending bookings in dashboard.

### M4: Client Can't Cancel Paid Booking Without Refund
If client cancels a paid booking, no refund is triggered through ClictoPay.

**Fix:** When client cancels a paid booking, trigger ClictoPay refund automatically.

### M5: PaymentResult Page is Minimal
Just shows success/failure with no booking details, amount, or reference number.

**Fix:** Show booking ID, amount paid, and reference number on success page.

### M6: No Email Verification Required Before Booking
Client can create a booking without verified email (if `email_verified_at` is null).

**Fix:** Already handled by middleware redirect to `/verify-email`, but worth noting.

### M7: No Booking Detail Page for Client
Client can see booking list but clicking a booking doesn't show a detail page with payment status.

**Fix:** Add booking detail view in client dashboard.

### M8: Complaint Form Doesn't Show Related Booking Payment Status
When client requests a refund, they can't see if the booking was actually paid.

**Fix:** Show payment status next to booking in refund request dropdown.
